# 100,000 active users × 1,000,000 photos

Assessment date: 2026-10-21. Application revision: `252d573bfdce059520839ff5c750f9683a45c299`.

Assumption requested by the user: no replica caps, and the largest suitable CPU/RAM sizes for every app. Existing Bicep replica ceilings and small instance sizes are **not** used to reject this target. Storage service limits, network, local disk, serial work and routing still apply. No cloud resources were provisioned or reconfigured in this assessment.

The current design is not validated for this target. Increasing app CPU/RAM and replicas alone does not provide the storage sharding or cache placement needed. A million-photo library and 100,000 independent active libraries are separate scaling questions. Local results below address the former; full distributed performance remains unmeasured.

## What was actually measured

`backend/scripts/benchmark_library_scale.py` uses the production `DatabaseBuilder`, `SearchDatabase` and lexical scoring function. It builds one synthetic million-row library through the actual reduction, FTS and indexing code, then measures gallery operations, FTS candidates and scoring, and a closed-loop shared-library thread workload. Assertions verify row count, nonempty pages, search matches and positive scores. The temporary database is removed after the run.

Fixture: ten subjects, common travel/outdoor tags, four cities, dates spread over ten years, ratings, likes, and person memberships. It excludes media, OCR payloads, EXIF richness, AI and face vectors. Its size is not representative of every real library. All dates fall before the assessment date.

Results: [raw JSON](library-1m-20261021.json). The measured tables follow below.

Reproduce from the repository root with backend dependencies installed:

```bash
.venv-photostore-tools/bin/python backend/scripts/benchmark_library_scale.py \
  --photos 1000000 --samples 12 \
  --output docs/benchmarks/library-1m-20261021.json
```

The local machine has limited free disk. The script checks headroom and deletes only its own temporary directory. CPU count and platform are captured in JSON. This is a macOS host test, not a largest-size Azure instance test. SQLite/OS caches are warmed by construction and compression; first-call timings are **not** cold-start timings. Twelve serial samples cannot estimate production tail latency reliably. Thread results include Python GIL effects and shared-file caching; they must not be multiplied into a distributed capacity claim. Timings exclude authentication, Azure Tables, manifest and delta checks, HTTP, network, response construction and browser rendering. The search case exercises candidate extraction, lexical scoring and an exact count, not every filter/ranking step of the HTTP route or its result cache.

## Measured results

Host: macOS-26.6.2-arm64-arm-64bit-Mach-O; 14 logical CPUs exposed; Python 3.13.2; SQLite 3.53.1. No CPU/RAM isolation or Azure-instance equivalence is claimed.

Build: **122.66 seconds**. Database: **615.57 MiB**. Gzip level 6: **170.60 MiB**, compressed in 9.69 seconds. Peak process RSS across the entire run: **656.44 MiB**, including imported backend dependencies and concurrent connections; this is not API replica sizing.

Each gallery operation returns 100 filenames; production workload arithmetic elsewhere uses 24 full photo summaries. Search retrieves up to 4,000 candidates. The serial p95 is the maximum of just 12 measured warm calls.

| --- | ---: | ---: |
| Gallery capture first page | 0.106 | 0.327 |
| Gallery capture offset 500,000 | 782.805 | 817.203 |
| Gallery capture offset 999,900 | 1572.397 | 1622.006 |
| Gallery name first page | 81.241 | 82.310 |
| Gallery rating first page | 0.066 | 0.097 |

Shared-library closed-loop workload: 80 operations per trial, 90% capture pages at varying offsets below approximately 625,000 and 10% beach search. These are threads in one process, not independent users, tenants or distributed workers.

| Threads | Operations/s | p50 (ms) | p95 (ms) |
| ---: | ---: | ---: | ---: |
| 1 | 1.864 | 573.424 | 951.679 |

The 16-thread trial regressed relative to four threads. CPU/GIL, storage and SQLite contention were not isolated; the result supports tuning processes/threads experimentally, not claiming a particular root cause or maximum throughput. At this fixture size, one base database per active library totals **64.55 TB** uncompressed or **17.89 TB** compressed for 100,000 libraries, before extra replica copies and scratch space. A 10-minute synchronized warm-up would transfer about **29.8 GB/s (238.5 Gbit/s)** of gzip payload alone. This is arithmetic from the fixture, not a measured cold-start test. Rich OCR/text or more person memberships can increase these sizes.

The default 1,200 MiB search cache budget fits only one of these 615.57 MiB bases per replica. Increasing this internal budget and disk provision can help, but arbitrary load balancing still duplicates working sets. A tuned large instance must be tested with its actual cache placement and multiple independent libraries.

## Workload and arithmetic

100,000 users × 1,000,000 photos = **100 billion photos**. Concurrent signed-in users, in-flight HTTP requests and requests/second are different quantities.

| Scenario | Assumption | Required API request rate |
| --- | --- | ---: |
| Normal interaction | Each user starts one request every 10 seconds | 10,000/s |
| Heavy interaction | Each user starts one request every second | 100,000/s |
| Request burst | Every user sends one request at the same instant | 100,000 in-flight requests initially; completion rate depends on latency |

Baseline request mix: 90% gallery, 10% search; 24 photos returned per request. These are explicit planning assumptions, not observed user behavior. Thumbnail and preview fetching are additional requests. Multiple API calls per UI action multiply the rate. Mean in-flight concurrency is approximately request rate × mean response time: 10,000 requests/s at 200 ms means roughly 2,000 in flight, despite 100,000 active users.

| Original size assumption | Per-user originals | All originals | Accounts at default 5 PiB capacity, rounded up |
| --- | ---: | ---: | ---: |
| 1 MB | 1 TB | 100 PB | 18 |
| 4 MB | 4 TB | 400 PB | 72 |
| 10 MB | 10 TB | 1 EB | 178 |

MB/TB/PB in this table are decimal; PiB is binary. These are capacity lower bounds with no operating headroom. At 50 KiB per thumbnail and 500 KiB per preview, derivatives add 5.12 PB and 51.2 PB respectively. With 4 MB originals, the combined 456.32 PB requires at least 82 default-capacity accounts before metadata, redundancy strategy, backups, versions, growth or traffic headroom. Azure-managed redundancy is not manually multiplied into the logical capacity figure.

Azure currently documents 5 PiB default account capacity, with higher capacity available by request. Blob/GPv2 request and network targets depend on region. These are service targets, not achieved benchmark rates. [Azure standard-account targets](https://learn.microsoft.com/en-us/azure/storage/common/scalability-targets-standard-account).

At 10,000 full 24-photo responses/s, the application needs to return **240,000 photo metadata entities/s** if every page requires fresh source rows. This omits auth, people, manifest, index, queue and write traffic. Azure Table Storage documents 20,000 transactions/s per account and up to 2,000 entities/s per partition for 1 KiB entities. Comparing entity demand to that reference gives an optimistic 12-account floor; actual sizing requires row sizes, scanned entities, query selectivity, and retries. A 50% target utilization gives 24 accounts for that illustrative metadata demand alone; it does not override the larger original-storage capacity requirement. Heavy interaction multiplies these figures by ten. [Table service targets](https://learn.microsoft.com/en-us/azure/storage/tables/scalability-targets).

For fresh 24-tile thumbnail pages at 50 KiB each, 10,000 pages/s implies 240,000 blob GETs/s and **98.3 Gbit/s** of image bytes. Browser/CDN hits reduce origin traffic, while retries, previews, originals and headers increase it. This is a deliberately uncached traffic scenario, not measured consumption. CDN configuration must preserve private-library authorization.

## Constraints that larger app instances do not remove

1. **One configured data account.** `backend/app.py` initializes Table/Blob/Queue clients from global storage settings; `deploy/resources.bicep` provisions one main data account and a separate worker cache account. There is no per-library data-account routing layer in this path. A larger app cannot turn one configured account into the dozens needed for this dataset. Introduce stable library-to-storage-shard mapping and route all relevant reads, writes, queues, authorization and index jobs consistently. Preserve managed identity and tenant isolation across shards.

2. **Local library replicas need locality.** `backend/search_db.py:open_database` loads a manifest, locates a per-library SQLite file, and downloads and unpacks the entire base on a cache miss. Every API replica has independent local ephemeral storage. More random replicas can increase cache misses and duplicate downloads. Use library-aware routing or a dedicated sharded query service, with bounded replication and failover. Set cache capacity from the active-library working set and local disk; high RAM alone does not enlarge ephemeral storage. Blob traffic, gzip CPU, scratch space and recovery storms must be measured.

3. **Deep pagination still does linear work.** `SearchDatabase.list_page` issues an exact count and `LIMIT/OFFSET`; large offsets walk skipped records. Name/location order uses `LOWER(filename)` without a matching expression index in `DatabaseBuilder.finish`. Additional CPU can increase total throughput across libraries but does not change those query shapes. Consider keyset pagination, an indexed normalized filename/order, and maintained counts. Validate ordering/filter semantics before changing them.

4. **Fresh metadata creates source-store fan-out.** `backend/routes/photos.py:list_photos` fetches full rows after SQLite chooses filenames; `_get_metadata_entities` uses OR-filter batches for gallery pages and point reads for search. OR queries are not equivalent to a batch of guaranteed point lookups; benchmark scanned entities and latency on million-row partitions. Consider a richer/versioned page read model or another bounded read path. Preserve freshness and deletion semantics.

5. **Partition and library serialization.** Metadata uses the library ID as its Table partition key. Different libraries can scale independently, but one busy library still has partition limits. Face assignment uses a renewable per-library Blob lease in `backend/clustering_lease.py`, so replicas can increase cross-library throughput while cooperating assignments for one library remain serialized. Benchmark the million-photo rebuild/checkpoint path and skewed libraries separately. More workers must not bypass the lease.

6. **Configured concurrency must use the larger instance.** The core deployment explicitly sets two Gunicorn workers and two request threads each. Removing replica caps and increasing CPU does not automatically increase process parallelism. Tune worker/thread counts against the selected instance and measured memory, CPU, source-store demand and Python scoring cost. A largest instance is not automatically the best latency or throughput per cost.

7. **Background work needs its own arrival-rate model.** If 1% of active users upload one photo/minute, arrival rate is 16.7 photos/s; if all do, it is 1,666.7/s. Each requires multiple persistence/processing steps. Sustainable queue drain must exceed arrivals, with latency targets and retry headroom. A one-time 100-billion-photo import finishing in 30 days requires about 38,580 completed photos/s. These are arithmetic requirements, not measured worker capacity. No end-to-end AI throughput claim is supported by the SQLite benchmark.

## Distributed test prepared, not executed

[concurrent-libraries.k6.js](concurrent-libraries.k6.js) provides an API-only ramp. It assigns one identity to each VU, rejects duplicate declared library IDs or fixture sizes other than one million photos, and counts index-building/partial responses as failures. Identity declarations must also be audited against actual server-side accounts and seeded libraries; the JSON declaration alone is not proof of tenant isolation. It samples deep offsets and name sorting and records separate gallery/search latency. k6 syntax was checked locally; the k6 runtime was unavailable, so runtime execution is unverified.

Keep the credential file outside the repository. Format: an array of `{ "libraryId": "...", "token": "...", "photoCount": 1000000 }`, with valid library-scoped sessions lasting through the run. Do not reuse one token/library for all VUs. Seeded metadata must include upload dates and sizes so legacy backfill does not confound the benchmark. HTTP GETs may still trigger normal index warming/rebuild behavior in the app.

Example for an already provisioned test deployment, from this directory:

```bash
k6 run -e BASE_URL=https://your-test-deployment.example \
  -e USERS_FILE=/absolute/private/path/library-sessions.json \
  -e VUS=100000 -e PERIOD_SECONDS=10 \
  concurrent-libraries.k6.js
```

Use distributed generators with a shared global VU ID allocation (k6 cloud/operator/execution segmentation), not independent runs that all reuse IDs starting at one. Provision identity entries for the entire allocated ID range, including any gaps. Pilot at 100 VUs before the full ramp. The script defaults to 100 VUs and ramps through 1%, 10%, 50%, 100%, holds for 30 minutes, then drains. At 100,000 VUs this is 1,000 → 10,000 → 50,000 → 100,000. Session tokens must remain valid. No credentials are supplied here and no remote test has been launched.

This is a **closed-loop** test: slower responses reduce achieved RPS. Passing latency thresholds does not prove offered throughput unless achieved throughput also meets the goal. Follow with a separate open-arrival-rate test at 10,000/s and 100,000/s; count scheduler drops and overload failures. [Grafana k6 execution and data parameterization](https://grafana.com/docs/k6/latest/examples/data-parameterization/).

Proposed acceptance targets, to agree before certification:

- At 100,000 independent active libraries, sustain at least 10,000 API requests/s during steady state; test the heavier 100,000/s case separately.
- Ready gallery p95 <500 ms, p99 <1.5 s; ready search p95 <2 s, p99 <5 s; error/unready rate <0.1%. These are chosen SLOs, not measured results or promises.
- Confirm every library actually has one million indexed metadata records; verify full media retrieval, no tenant leakage, valid counts and deletion visibility. The API script checks readiness and gallery counts, not the full correctness contract.
- Record per-shard Table entities scanned/returned, throttles/retries, account capacity/ingress/egress, Blob GETs/bytes, cache misses/downloads, API CPU/RSS/disk and queue age. Measure generator CPU/network and scheduler drops so the injector cannot hide saturation.
- Repeat warm steady state, cold placement, scale-out and replica loss, storage throttling, 24-hour churn, and hot-library skew. Use explicit bounds on index freshness and backlog recovery. Increase offered load until an SLO fails to determine capacity rather than assuming linear scaling.
- Run separate media delivery, login/token refresh, upload/finalize, index freshness, album/person mutation and AI/face-processing tests with realistic data and failure conditions. The supplied harness covers none of those paths beyond normal gallery/search response building.

A metadata-only distributed test can validate query/application behavior at 100 billion records without storing hundreds of PB of originals. It **cannot** certify full media storage, delivery or ingestion at that scale. Full-fidelity qualification requires a funded environment, actual shard configuration, seeded libraries, load generators and deployed-instance metrics. Exact replica counts and maximum-size-instance performance remain unknown until that test is run; multiplying this laptop's operations/s by replica count would be misleading.
