## Finding

The large burst is caused by unfinished upload reservations from October 27 leaking into the gallery's sort index. A separate, small set consists of older finalized files with failed thumbnail processing.

| Classification | Confirmed thumbnail 404s |

| Unfinalized upload reservation from October 27 | 2,264 |

The capture spans October 28, 09:15:21–09:16:05 UTC (10:15:21–10:16:05 Stockholm). All 2,267 HTTP 404 responses are direct thumbnail GETs from the development storage account, with `x-ms-error-code: BlobNotFound`. None uses an immutable `derived/` thumbnail path. All 2,267 map to distinct entries in the embedded sort index.

There are also 2,380 entries with status 0, meaning no HTTP response was recorded. These are not counted as missing blobs. The capture does not establish missing original images.

## Live metadata confirmation

The `owner` partition of `photometadata` in `forenklaprep1devmqwhngus` contains 13,749 rows, matching the captured sort-index row count.

All 2,264 reservation-related failures still have `pendingAnonymousBlob`, no `anonymousImageId`, and no `uploadDate`. Their captured processing statuses are all null. The partition has **3,265** such reservation-only rows in total, all initialized on October 27 between 19:21:30 and 19:35:26 UTC (**20:21:30–20:35:26 Stockholm**). The capture only proves 404s for the 2,264 that received that response.

No reservation UUID among these 3,265 rows is referenced by another finalized metadata row in the same partition. This excludes that particular renamed-file explanation in the scanned metadata; it does not replace authoritative ownership checks before any future cleanup.

Example: `050697.png` has a pending blob UUID, expected hash, total size, empty received ranges, and an upload-start timestamp, but no finalization or processing fields. The gallery requests `thumbnails/050697.png`, because no permanent physical identity or derivative receipt exists.

These records establish unfinished finalization and are consistent with the interrupted upload. They do not prove which bytes reached Blob Storage, whether the browser stopped before commit, or whether an attempted finalize failed. Empty received ranges alone do not establish that no direct-to-Blob transfer occurred.

## Code path

- `backend/storage_utils.py:reset_upload_tracking_and_reserve_blob` persists upload reservations in the same metadata partition as finalized photos, before finalization.
- `_build_user_sort_index_snapshot` scans this partition and excludes deleted rows, but does not exclude reservation-only rows.
- `_sort_index_row` emits every nonempty filename. Without a valid thumbnail receipt or `anonymousImageId`, its thumbnail path falls back to the original filename.
- Upload chronology can fall back to `upload_started_at`, placing unfinished reservations in the gallery's recent chronology.

This explains why a successfully served sort index produces thousands of requests for thumbnail filenames that were never assigned as permanent physical identities. The current Container Apps all report `Running` with provisioning state `Succeeded`; the storage account reports provisioning state `Succeeded`. These control-plane states do not prove worker processing success.

## Recommended correction

Exclude demonstrably reservation-only rows from catalog publication using explicit finalization evidence, while preserving legacy finalized records and legitimate photos whose derivatives are still processing. Apply the same rule to full and incremental sort builds and review the library database/access projections for consistency. Do not use thumbnail completion as the admission rule.

After deploying the correction, rebuild the affected published catalog so existing reservation rows disappear. Treat cleanup of abandoned reservations as a separate recovery operation with active-upload and physical ownership checks; deleting blobs solely because a reservation looks old is not justified by this audit. Investigate the three finalized thumbnail failures separately.

## Local correction

The follow-up code change adds a shared admission rule to sort, access, and SQLite library projections, covering bootstrap builds, full scans, and incremental updates. A row is excluded only when it has `pendingAnonymousBlob` and lacks all retained finalization evidence (`uploadDate`, `anonymousImageId`, `fileHash`, `perceptualHash`, `mimeType`, `verification_status`). Legacy rows without a reservation remain eligible, including those using only `upload_started_at` as their date. Finalized photos stay visible regardless of processing outcome or a subsequent pending replacement upload.

Projected reads include the admission fields. Sort schema v5 requests a full rebuild of older sort snapshots through the existing schema-upgrade path. Existing access and SQLite catalogs still require a rebuild or targeted dirty-row refresh; deployment alone does not synchronously repair all published artifacts. Reservation and blob cleanup is not part of this change.

Applying the guard to the saved live metadata excludes exactly the 2,264 reservation-related 404 entries and retains the three finalized processing failures. No deployment or remote data writes were performed.
