## 1. [P1] Equal manifest timestamps still allow an older payload to overwrite a newer shared cache

Locations: `frontend/src/services/localSortIndex.ts:115`, `frontend/src/services/localPeopleIndex.ts:98`, and `frontend/src/services/localAlbumsIndex.ts:98`.

The new transaction makes the read/compare/write atomic, but its comparison uses `updatedAt`. That field belongs to the manifest: a dirty v2 manifest can advertise the same `sourceVersion` and `updatedAt` as the eventual clean v2 manifest while the downloadable body still contains v1. Dirty marking sets `updatedAt` to `sourceVersion` (`backend/storage_utils.py:5128`); clean publication also sets it to that source version (`backend/storage_utils.py:5478`). Therefore, equal manifest timestamps do not establish equal body freshness. Missing timestamps also unconditionally allow replacement.

Reproduced with the actual sort loader, independent module contexts representing tabs, and shared fake IndexedDB:

1. Tab A receives manifest v2 with a nonempty timestamp and starts downloading the old v1 body; response completion is delayed.
2. Tab B receives that same manifest timestamp, downloads the published v2 body, and persists rating 5.
3. Tab A finishes with the old body containing rating 1. The persisted timestamps are equal, so `current.updatedAt <= value.updatedAt` allows its stale write.
4. Tab B continues to show 5 from memory, but a fresh module reload reads the overwritten persistent record and returns **1**, expected **5**.

This is the outstanding cross-tab defect from pass 5, with an additional reproduction using explicit equal timestamps to test the attempted fix. It is not a newly introduced regression. The two failing assertions represent one issue. The People and Albums caches contain the same faulty comparison; the executable reproduction covers Sort.

Compare the actual persisted `payloadVersion` within the same read/write transaction, retaining the local generation fence. Handle unknown payload versions conservatively so they cannot replace a known newer body merely because a manifest validator matches. The existing stored record already carries the body revision separately from the manifest revision.
