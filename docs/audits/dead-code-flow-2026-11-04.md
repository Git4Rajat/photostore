The flows below were then traced through selected implementations and tests. Production traffic, deployed flags, real storage failures, and exhaustive thread interleavings were not exercised.

## 2. Findings, ordered by practical impact

Priority labels indicate suggested repair order, not a claim of a currently observed production incident.

### F1 — Sort deltas are published but omitted from the serving response

**Priority: P1. Reproduced.**

Path:

```text
metadata/index work
  → storage_utils._sort_publish_delta
  → manifest retains base sourceVersion and increments deltaSeq
  → get_index_manifest_summary
  → photos_sort_index
  → localSortIndex.fetchLocalSortIndex
```

Line-level evidence:

- `backend/storage_utils.py:5979`: `_sort_publish_delta` writes the delta and updates the manifest sequence.
- `backend/storage_utils.py:8790`: `get_index_manifest_summary` returns its dictionary.
- `backend/storage_utils.py:8797`: code intended to populate `summary['delta_seq']` is after that unconditional return. `summary` also has no preceding assignment in this function.
- `backend/routes/photos.py:1123`: the route defaults the absent summary field to zero and mints no delta URLs.
- `frontend/src/services/localSortIndex.ts:303`: the client consumes that zero sequence.
- `frontend/src/services/localSortIndex.ts:307`: an existing cache with the same base version and zero sequence is considered current.
- `frontend/src/services/localSortIndex.ts:323`: the incremental application branch requires a positive newer sequence and supplied delta URLs.

Reproduction: a manifest containing `deltaSeq=3` produces an available response with `deltaSeq=0` and `deltaUrls=[]`.

Implication: while this delta publication path is used, a client can reuse stale base rows; a fresh client also receives only the base artifact. Local edit overlays can mask a caller's own edits but cannot establish correctness for other clients' changes. This is not just three harmless unreachable lines.

Repair boundary: make the summary a complete, typed projection of the manifest; test the producer → summary → route → client contract, not only delta construction.

### F2 — Photo writes can report success after persistence failed

**Priority: P1. Reproduced.**

Path:

```text
store.ratePhotos / toggleLike / rotation save
  → pending edit journal
  → photo route
  → _update_metadata_entity_fields
  → failure returns None
  → route sends success
  → client confirms its optimistic edit
```

- `backend/app.py:3408`: `_update_metadata_entity_fields` returns `None` for a failed lookup, deleted source, or exhausted write retries.
- `backend/routes/photos.py:1505`: single rating discards that return value and responds with `success=True`.
- `backend/routes/photos.py:1537`: bulk rating similarly counts an attempted update as successful without inspecting the returned entity.
- `backend/routes/photos.py:1574`: like also ignores the write result.
- `frontend/src/mockups/prototype/store.tsx:1325`: the like flow confirms the pending edit on the fulfilled HTTP request.

Reproduction: the real helper executes against an injected unavailable metadata table; the real rating route responds HTTP 200 with `rating=5`, although no rating was stored.

Implication: the UI may affirm a change that never persisted. Its confirmed overlay then has to contend with conflicting server projections. The client consistency machinery cannot compensate for an inaccurate source acknowledgement.

Repair boundary: return a typed write outcome or raise an explicit persistence error. Require routes to acknowledge committed values. Keep source commit and derived-index publication outcomes separate so a committed source is not confused with an unsaved one.

### F3 — Automatic retries can execute non-idempotent mutations twice

**Priority: P1. Reproduced.**

- `frontend/src/services/httpClient.ts:106`: a request with no response is retryable for every method.
- `frontend/src/services/httpClient.ts:111`: every HTTP 503 is treated as retryable for every method.
- `frontend/src/services/httpClient.ts:219`: `requestJson` performs the retry.
- `backend/routes/photos.py:1555`: like is a toggle, not a request to set a desired state.
- `backend/routes/albums.py:191`: album creation generates a fresh UUID on every call.

The premise in the transport comment—no response proves that the request never ran—is not established by this implementation. The response can be lost after the server committed.

Reproduction: the first POST applies a like toggle and then throws a simulated network error. The real `requestJson` retries; the second POST toggles it back. One user action results in two server executions and a final `liked=false`.

There are also app-generated 503 responses in this repository, including wave finalization's post-handler binding failure. A status code alone does not establish whether side effects happened. Wave operations have explicit replay identities; unrelated mutations do not all have that protection.

Repair boundary: use mutation-specific retry policy and server-enforced idempotency where needed. Prefer a desired-state like operation. A correlation ID is not an idempotency mechanism unless the server persists and enforces it.

### F4 — A failed trash-index write is not repaired by delete replay

**Priority: P1. Reproduced.**

Path:

```text
delete photo
  → authoritative metadata becomes deleted
  → secondary trash-index write fails and is swallowed
retry delete
  → already-deleted early return
  → secondary index remains absent
Recently Deleted
  → initialized trash index is trusted
  → deleted photo is omitted
```

- `backend/app.py:14177`: `_trash_index_add` logs and suppresses write failures.
- `backend/app.py:14260`: `_mark_processing_deleted_for_file` returns immediately for an already-deleted source.
- `backend/app.py:14275`: the first attempt commits metadata before updating the secondary index.
- `backend/app.py:14193`: `_trash_index_entries` backfills metadata only when there is no initialization marker; an initialized index is queried directly.
- `backend/routes/photos.py:1325`: Recently Deleted uses those entries.
- `backend/routes/photos.py:1415`: restore-all also takes its filename set from those entries.

Reproduction: initialize the trash index, fail its next upsert, delete a photo, retry the delete, then list trash. Metadata is deleted; the trash list is empty.

Implication: a photo can disappear from the gallery and also be missing from normal recovery UI. This is not permanent loss of the original bytes. The retention sweep independently scans metadata (`backend/app.py:13812`), so it may still purge the source later.

Repair boundary: make secondary-index repair part of replay, or persist a repair intent with the source mutation. Preserve the original deletion time/status snapshot while repairing the index.

### F5 — The active index-status poller calls the wrong service

**Priority: P2. Reproduced and traced through role registration.**

- `frontend/src/components/AppServicesProvider.tsx:1023`: a cold/building library reports the `session` source as building.
- `frontend/src/services/indexBuilding.ts:2`: the poller imports plain `get`.
- `frontend/src/services/indexBuilding.ts:61`: it requests `/api/tools/indexes/status` through that core client.
- `frontend/src/services/apiClient.ts:127`: plain `get` uses `apiClient` / `API_BASE_URL`.
- `frontend/src/services/apiClient.ts:133`: `getTools` is the separate indexer client.
- `backend/app.py:18372`: tools routes are registered on the indexer role; core's registration list excludes tools.

Reproduction records the poller's selected client as `core` for this tools path. The role-registration tests independently verify the service split.

Implication: in the split-service configuration represented by this code, the poller can repeatedly receive 404 and fail to clear its building source or notify `onIndexReady` consumers. Other event or page-refresh paths may still update data; this does not prove the entire gallery is blocked.

Repair boundary: put endpoint ownership in one routing authority or use the correct explicit client. Add a test that checks the chosen service, not merely a mocked successful `get` response.

### F6 — Shared-library likes use a library identity as the actor

**Priority: P2. Reproduced. Product semantics should be confirmed before migration.**

- `backend/app.py:2757`: `_require_user_id` explicitly returns the active **library** ID.
- `backend/routes/photos.py:1556`: like calls that compatibility shim.
- `backend/routes/photos.py:1569`: the returned library ID is used for membership in `likedBy`.
- `backend/app.py:2519` and `backend/routes/photos.py:1637`: read projections use the same identity convention.
- `backend/storage_utils.py:5950`: the shared sort projection computes `gallery.liked` from the row's partition key.

Reproduction: Alice and Bob each like a photo in the same library. Alice's action produces one like; Bob's action removes it because both operate on the same `shared-library` entry.

If likes are intended per member, actor and partition identity are conflated. If they are intended as a library-wide favorite switch, the `likedBy` model and count semantics are misleading. Either way, this boundary needs an explicit decision.

Repair boundary: resolve `(account_id, library_id)` explicitly for actor-sensitive operations. A per-account fix also needs a read-projection strategy: one library-wide index cannot contain a different personalized `liked` value for every member.

### F7 — Soft delete can overwrite a concurrent metadata edit

**Priority: P2. Reproduced with an injected interleaving.**

- `backend/app.py:14253`: soft delete reads an entire metadata entity.
- `backend/app.py:14275`: it upserts that snapshot without an ETag condition.
- `backend/app.py:14576`: restore follows a similar whole-entity read/mutate/upsert pattern.
- By contrast, `backend/app.py:3408` uses conditional update/retry for ordinary metadata edits, and `storage_utils._commit_worker_processing_results` rechecks source, lease, and generation.

Reproduction: deletion reads a row with rating 1; another writer commits rating 5; deletion then upserts its old snapshot. Final stored rating is 1.

This establishes a lost update, not every possible delete/worker race. The worker's own fences remain valuable and must be preserved.

Repair boundary: express deletion/restoration as conditional transitions against the current entity. Persist only intended fields, with retry and source-state checks. Add both delete-versus-edit and restore-versus-processing interleavings.

### F8 — Corrupted Uploads currently reports a result without checking

**Priority: P2. Static verification.**

- `frontend/src/mockups/prototype/PrototypeApp.tsx:190`: the active menu's handler only shows `Corrupted uploads: all clear`.
- The 168-line `frontend/src/components/CorruptedUploadsPage.tsx` is outside the active entry graphs.

This flow has neither navigation nor an authoritative query in its active handler. Retiring the old page without recognizing this gap would preserve an inaccurate success-like message.

Repair boundary: implement a real inspection flow, or remove/disable the claim until one exists. This is a product gap associated with the UI migration, not an automatic reason to revive the whole old frontend.

## 3. Latent defects kept separate from active-path findings

**L1: GET coalescing ignores `config.params`.** `frontend/src/services/httpClient.ts:265` keys concurrent GETs by session scope, base URL, and URL string. Two requests with the same URL but different `config.params` share the first result. The isolated probe requests pages 1 and 2 and gets `[1, 1]` from one network call. Current production callers found in this pass put paging parameters into URL strings, so no active affected call site was established. Fix before adopting `config.params` more broadly.

**L2: `useIndexStatus` returns a new snapshot object on each read.** `frontend/src/services/indexBuilding.ts:117` wraps `indexStatus` in a spread inside `useSyncExternalStore`'s snapshot getter. The probe confirms two unchanged reads produce different references. Its only source consumer is the disconnected legacy `ToolsPage`. This is dormant code debt, not evidence of an active rendering loop. Remove it with the retired page or stabilize the snapshot before reuse.

## 4. Flow-by-flow map and branch review

### 4.1 Startup and role selection

```text
backend/entrypoint.sh
  bootstrap pending + worker role → wait without importing app
  wave-recovery → python -m wave_recovery
  index-worker → app.run_index_worker
  cluster → app.run_clustering_worker
  vision → app.run_ipworker
  HTTP role → Gunicorn imports app
    → storage configuration and shared globals
    → imports all route modules
    → registers role-specific blueprints
```

**Reachability:** worker functions and Gunicorn hooks are live entry points even without ordinary callers. `wave-recovery` is an explicit executable path; an absent regular app import is not evidence it is dead.

**Debt:** HTTP service separation narrows routes, but every role still imports the large shared `app.py` module. The route modules call back into its globals. There are approximately 2,367 `app.` occurrences across route files. That is a lexical coupling measure, not 2,367 distinct dependencies.

**Refactor:** extract application construction/configuration from role runners and domain services. Keep role-route contract tests. Do not promise memory/cold-start improvements until measured.

### 4.2 Authentication, tenant selection, and session changes

```text
password login → user lookup / password verification → app-issued session
Entra login → Microsoft token exchange → app-issued session
request → _resolve_session_payload → _require_library_context
  → current account / tokenVersion
  → membership check for shared library
  → (account ID, active library ID)
compatibility shim → library ID only
```

Source anchors: `backend/routes/auth.py:28`, `:56`; `backend/app.py:2618`, `:2657`, `:2757`; `frontend/src/services/authClient.ts:151`.

**Branches:** no-token local password mode, invalid session, deleted account, stale token version, removed membership, transient lookup failure. Transient account/membership failures yield 503 rather than being treated as absence. Preserve this distinction.

**Debt:** the name `user_id` means account in some places and library partition elsewhere; F6 is a concrete result. `password_auth.py`'s single-owner module prose also predates the multi-account route behavior.

**Refactor:** introduce explicit account/library context names or types; avoid a sweeping mechanical rename. `libraryClient` additionally uses its own `fetch` transport rather than `requestJson`; retry/session behavior should be made explicit before consolidating them.

**Debt:** multiple views of readiness—manifest availability, worker status, search DB partial build, client local indexes, event notifications—are coordinated across provider, store, and global services.

**Refactor:** define a small readiness/status contract. Preserve distinct empty, building, unavailable, dirty, and partially available states.

### 4.6 Finalization and browser result application

```text

  → validate bindings / capability / finalization lease
route → validate file/hash/size → check physical blob
  → storage_utils.finalize_uploaded_file
     exact duplicate → canonical filename, no new generation
     new/replaced source → filename + generation + metadata + hash ownership
  → prepared processing / metadata packet application
  → legacy queue hooks (wave-owned guards suppress legacy execution)

```

Source anchors: `backend/routes/upload.py:449`, `:647`; `routes/upload_wave_live.py:59`, `:103`; `storage_utils.py:11612`.

**Debt:** single and batch routes repeat much of the same post-finalization sequence, including stamping, client processing, packet receipts, queueing, and response creation. Their common behavior needs one result-producing service with thin single/batch adapters.

**Important recovery boundary:** an after-request 503 may follow a successful source commit. Preserve `_verified_replay` and `finalized_replay`; do not replace them with naive re-finalization.

Late processing flows into `apply_client_processing_results_for_file` (`storage_utils.py:11203`) and the 911-line `_apply_client_processing_results` (`:10232`). The wrapper distinguishes worker/consolidated versus legacy browser behavior, validates revision/fence/lease, captures immutable artifacts, and commits partial failures. Extract per-step decisions and output preparation while retaining one explicit final commit authority.

### 4.8 Worker dispatch, contention, and failure paths

```text
queue wake → validate type / role / wave / outbox / intent revision
  disabled or stale → noop
  live owner / claim contention → retain receipt, retry
  valid claim → publication guard + stage execution lease
    vision → claim source lease → processing → fenced result commit
    cluster → frozen immutable inputs → decision journal → assignment receipt
    index → exact obligation set → publish/verify outputs → completion receipt
  durable progress → checkpoint + continuation
  no progress / failure → bounded retry accounting + failure capsule
  complete/cancelled → finish pending maintenance/successor handoffs
```

Source anchors: `wave_runtime.py:225`; `upload_wave_execution.py:527`, `:755`, `:823`; `wave_assignment.py`; `wave_assignment_files.py`; `wave_assignment_resume.py`; `execution_lease.py`; `index_work.py`.

**Preserve:** stage-dispatch ownership is separate from execution ownership and source-result ownership. Their leases are not duplicates. Immutable processing generation, attempt fence, artifact receipt, assignment receipt, publication obligation, and completion receipt prove different boundaries.

**Debt:** `consume` still mixes admission, role orchestration, diagnostics, continuation accounting, publication setup, and several exception policies. Extract stage handlers with explicit outcomes; do not merge retry counters merely because they have similar numeric defaults.

Detailed outcome paths in `wave_runtime.consume` and its source settlement helpers:

| Condition | Current action | Refactor invariant |
|---|---|---|
| Execution disabled | `noop`, no app import needed | Disabled path must not perform storage/queue work |
| Stage does not belong to process role | Raise before execution | A role cannot execute another role's stage |
| Wrong scope, missing outbox, stale/missing/failed work revision | `noop` | An advisory message cannot invent authority |
| Wave already complete/cancelled | Retry unfinished durable handoffs | Completion is not permission to drop unfinished handoffs |
| Outbox no longer eligible | Repair current-stage relay, then `noop` | Old-stage delivery can repair a committed transition |
| Live execution owner or dispatcher contention | Retain receipt / `retry` | Contention must not be counted as a model attempt |
| Dispatch attempt exceeds five | Persist failure, mark intent failed, require operator retry | No unlimited dispatch-failure loop |
| Same-stage slice with durable progress | Release/checkpoint, relay continuation | Persist progress before acknowledging the wake |
| Same-stage slice without progress | Record `NoProgress`, release without refund, retain receipt | An evaluation loop must not manufacture success/progress |
| Artifact cleanup busy | Retain receipt and consume bounded dispatch budget | No unbounded delayed self-wake chain |
| Ownership lost to a currently live owner | Deferred release, retain receipt | Hand ownership over without another source attempt |
| Vision coordination contention with committed progress | Reset consecutive budget, delayed durable continuation | Reconcile committed outputs rather than recompute models |
| Other exception after durable progress | Record details, refund/reset based on progress, rethrow | Retry accounting must reflect durable progress |
| Source compute failure | Source budget currently one attempt (`wave_settlement.py:7`) | Failure settlement is distinct from successful source completion |
| Repeated evidence-inspection failure | Separate inspection budget of three | Infrastructure/evidence errors are not successful processing |
| Persistently blocked source without live owner | At least three checks and 300-second grace, then witnessed settlement | A silent skip must not bypass the publication barrier |

The source settlement defaults are intentionally different from the dispatch budget. A blanket retry helper would erase that distinction. The source contract also distinguishes `settled`, `excluded`, `deleted`, `superseded`, and `failed_exhausted`; completion can explicitly be `applied_with_failures` rather than silently implying every model step succeeded.

No new defect in these lease/receipt handoffs was established by this pass. Existing selected recovery/ownership tests passed; that is narrower than a production liveness proof.

### 4.11 Delete, restore, and purge

```text
small delete → inline soft-delete service
large delete → persisted filename payload → library-operations queue → same service
soft delete → status snapshot + deleted state + trash index + face visibility + dirty indexes
restore → saved statuses + active state + trash removal + face visibility + dirty indexes
hard purge → source cleanup fence + strict cascades + blob/row/index removal
retention sweep → independent metadata scan → hard purge
```

**Findings:** F4 and F7 concern the soft-delete side. They do not justify weakening hard-purge fences or strict face cascades. Request and background soft delete already share an implementation; retain that convergence.
