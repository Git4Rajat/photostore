## [P1] Conflicting then matching unversioned reads can still erase a versioned reconciliation obligation

Location: `frontend/src/services/pendingEdits.ts:172–177`; the same-version conflict gate at `:146` makes subsequent recovery fail.

The new guard prevents a matching unversioned row from directly clearing a versioned pendingProjection. However, a *conflicting* unversioned row first overwrites that versioned projection with an object containing no version. A subsequent matching unversioned row then clears this replacement, losing the original unresolved publication conflict indirectly.

Reproduced sequence:

1. Save rating 5 and acknowledge it in v2.
2. Observe rating 2 in v3; capture the required source check. The backend's current rating is 2.
3. Receive a fresh but unversioned page containing stale rating 4. It replaces the v3 projection evidence with `{value: '4', readId: ...}`.
4. Receive another unversioned page containing stale rating 5. Since the replacement has no version, the match clears it.
5. Complete the valid v3 source response with 2. It is rejected because its projection evidence was replaced/cleared. No follow-up source requests remain, and hasPendingEdits is false due to the earlier v2 acknowledgement.
6. Even reading v3/rating 2 again does not restore demand: the persisted projectionVersion is already v3, while a conflicting versioned row creates pendingProjection only when its version is strictly greater than the floor.

**Actual UI overlay: 5; required eventual authoritative value: 2.** The reproduction fails both without reload and after reloading journal state between the lost source response and the repeated v3 read. This can therefore mask the later source value until another newer publication or conflicting fresh unversioned observation happens to restart verification.

Unversioned photo pages can follow a versioned download when a library crosses the client-index size threshold or uses a fallback. Such pages carry no publication ordering, so another fetched page can still contain older data. Their arrival order cannot establish that v3 has been resolved.

Recommended correction: preserve the versioned reconciliation obligation separately from provisional unversioned observation evidence. Unversioned observations may demand or restart a bounded source check, but neither a conflicting unversioned row nor a later match may remove an unresolved versioned obligation. Resolve that obligation only through an applicable authoritative source result or a matching publication at least as new as its version. Keep request fencing separate so replacing an in-flight check still leaves a follow-up demand.
