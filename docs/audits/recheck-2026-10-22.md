## 1. [P1] Rotation is marked saved before its backend write finishes

Location: `frontend/src/services/localSortIndex.ts:395–396`; caller `frontend/src/mockups/prototype/store.tsx:1289–1291`, dispatched by `frontend/src/mockups/prototype/components/PhotoViewer.tsx:130–134`.

`patchLocalSortIndexRow` now creates and immediately confirms a journal receipt. Its remaining production caller is rotation: PhotoViewer applies the store rotation first, then calls `setPhotoRotation` asynchronously. The journal therefore exposes an unsaved rotation as a confirmed field eligible for authoritative reconciliation. If a refresh/source check runs while that write is still outstanding, the backend correctly returns the previous rotation; reconciliation adopts it and the UI loses the user's pending change. The eventual successful rotation request does not confirm a request-owned journal entry, so it cannot repair the receipt immediately.

**Reproduced through the actual index/journal/reconciliation services:** begin from rotation 90, apply the viewer's optimistic patch to 180, and reconcile against source 90 while the save has not completed. The next index read returns **90**, expected **180** while the write remains pending.

Correction: enroll the actual rotation write in begin/save/confirm/rollback, confirm only after that write succeeds, and serialize overlapping rotations through the same entity queue. A UI patch must not itself be treated as a persistence acknowledgement.

## 2. [P1] A newer matching unversioned page does not invalidate an older source response

Location: `frontend/src/services/pendingEdits.ts:153–158`; source acceptance at `:307–308`.

Fresh-read identity is advanced in `lastReadOrder`, but `pendingProjection` changes only when the incoming value conflicts with the current receipt. A newer matching page leaves the older check's evidence intact. `acceptSourceEdits` compares publication version and pending projection, neither of which changes for that matching unversioned read, so it accepts an obsolete source response.

Example: receipt 5; page R1 reports 2 and starts a source read that observes 2; a later page R2 reports the now-current 5; the delayed R1 source response then arrives. The receipt becomes 2 even though R2 is newer. The check clears pending state, and the incorrect canonical receipt is persisted. The existing regression exercises a newer *conflicting* read, which changes pendingProjection; this matching case does not.

**Reproduced:** the R1/R2/source-response sequence returns **2**, expected **5** or retention of 5 until a new source check resolves R2's evidence.

Correction: fence source reads with the latest applicable read identity, including matching observations. When an unversioned match cannot prove convergence, preserve the demand for verification with updated evidence rather than allowing the earlier read to resolve it.

## 3. [P2] Failed overlapping person renames can permanently restore a failed predecessor

Location: `frontend/src/mockups/prototype/store.tsx:2047–2051`; secondary overlay at `:536–553`.

The journal tracks failed predecessors, but the independent `personNameEditsRef` chain does not. Rename Original → First → Second while both saves are outstanding. First fails while Second is current, so First's catch returns without marking its shadow edit failed. When Second fails, it reinstalls First as `previousEdit`. Its `saved` flag remains false, so `reconcilePersonName` keeps overlaying First even on subsequent successful page fetches returning Original. The authoritative journal's correct rollback does not remove this separate overlay.

**Reproduced through StoreProvider:** fail both rename promises, then refetch People from the unchanged backend. The UI still shows **First**, expected **Original**.

Correction: use the journal as the single rename transaction chain, or mark and skip failed shadow predecessors and retain a confirmed baseline. A refetch must not be overridden by a failed edit.

## 4. [P2] Album fallback reads never revalidate acknowledged name receipts

Location: `frontend/src/mockups/prototype/store.tsx:1135–1137`.

The fallback `GET /albums` path applies saved name receipts without capturing fresh-read tokens or registering projection observations. After source confirmation, an acknowledged receipt is passive. A later rename by another client can therefore be returned by the actual fallback API repeatedly while the UI continues masking it with the old receipt. Running reconciliation explicitly does not help: no conflict was registered, so there is no selected source request. This applies while the client Albums index remains unavailable, including during recovery from index/storage failures.

**Reproduced through StoreProvider:** confirm receipt Saved, acknowledge it from source, make the local index unavailable, and have `/albums` plus source both return Later. A forced album refresh and reconciliation still show **Saved**, expected eventual **Later**.

Correction: give successful fallback reads the same scoped fresh-read observation/reconciliation flow as the server-paged photo path, preserving saved overlays while verification runs.

## Existing defects also reproduced, not counted above

- **Persistent cache writes are not fenced by invalidation.** The new generation checks protect the memory cache but the asynchronous IndexedDB writes remain unconditional in Sort, People, and Albums. Reproduced with the actual Sort loader and fake IndexedDB: both reads receive validator v2, the first body is the stale v1 payload while rebuilding, the second body is v2 after publication; the invalidated first download finishes last and overwrites IndexedDB. Memory still returns the newer rating 5, but after module reload the current v2 validator reuses the older persisted rating **1**. A dirty v2 manifest becoming clean v2 makes this validator sequence realistic. The unconditional write and equivalent invalidation race already exist in HEAD. This remains a gap in the cache-ordering remediation, not a new regression attributed to it.
- **Album rollback captures an optimistic name as its baseline.** Two failed album renames leave First instead of Original. This stale UI rollback also exists before this diff; unlike the new People shadow map, it does not independently force the failed value over every subsequent refresh. Retained as a related regression case, not counted as an introduced finding.
