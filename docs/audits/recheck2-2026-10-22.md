## 1. [P1] Matching unversioned reads still mishandle source-check ordering

Location: `frontend/src/services/pendingEdits.ts:153–161`, with acceptance checks in `acceptSourceEdits`.

Clearing pendingProjection on a matching page fixes one sequence but does not establish a complete read fence. Two cases reproduce:

1. **An initial source check has no pending projection to clear.** Confirm local rating 5 and capture its initial source request, receive a fresh unversioned matching page at 5, then complete the older source request with 2. Both request and field still have undefined projection evidence, so the stale response is accepted and persists **2**, expected retention of **5** until a check against the latest read evidence resolves it.
2. **An unversioned match cancels a newer versioned conflict without replacement verification.** Acknowledge Alice at v2, observe Bob at v3 and capture its source check, then receive matching Alice from an unversioned page. The new branch clears the v3 conflict despite having no publication revision. The valid Bob response is rejected, no source requests remain, and the UI retains **Alice** even though the current source is **Bob**. Its v2 observedVersion also makes hasPendingEdits false. Trying another reconciliation pass does not recover because there is no selected request.

An unversioned page may itself be a stale projection. Matching a receipt is insufficient publication evidence. Fence every applicable observation, including initial checks with no conflict object, and preserve/renew verification demand when a matching observation cannot prove it supersedes the publication being reconciled.

## 2. [P2] Overlapping failures still restore an optimistic value instead of the saved baseline

Locations: `frontend/src/mockups/prototype/store.tsx:1337–1340` and `:2070–2072,2088–2095`.

The journal's failed-predecessor traversal is correct, but the store's fallback values are captured from already optimistic UI state:

- **New rotation flow:** from saved 90, queue 180 and then 270 with previous values 90 and 180. Fail both serialized requests. The journal removes both failed fields, but the second catch unconditionally applies its captured previous value **180**, expected **90**. That failed value is visible through photoById and the raw collection until a later refresh repairs it. The first failure can also patch raw photo arrays while a newer rotation remains pending.
- **Person rename:** Original → First → Second, fail both. The new loop correctly skips the failed First edit, but falls back to the second edit's serverName, which was captured from the optimistic First UI. It displays **First**, expected **Original**. The old indefinite shadow overlay is fixed: another successful fetch now repairs this value. The immediate rollback remains incorrect.

Carry the last confirmed baseline through the transaction chain, and derive rollback UI state from the surviving current receipt or that baseline. Avoid reapplying an arbitrary captured optimistic value after the journal has rejected it.

## 3. [P2] Successful rotation saves do not restart index recovery polling

Location: `frontend/src/mockups/prototype/store.tsx:1333–1335`.

The new success handler only confirms the journal entry. Unlike rating, liking, and renaming, it neither requests job polling nor schedules reconciliation/refresh. `setPhotoRotation` is a plain POST wrapper and supplies no nudge. hasPendingEdits is checked by an already running poller; it does not itself start polling.

In an idle session whose job poller has stopped, rotating a photo therefore leaves the new receipt unresolved and published index/thumbnail changes unobserved until a focus, navigation, or unrelated mutation supplies another trigger. This matters for deployments with push disabled (the infrastructure default), and when push is unavailable. The optimistic orientation is visible, but the recovery path promised by this change does not run automatically.

**Reproduced through StoreProvider:** complete a successful rotation save; the requestJobPoll boundary is never called. The pending-rotation test separately verifies that the receipt becomes eligible only after success.

Nudge the existing bounded recovery path after confirming the write, with the usual session guard.
