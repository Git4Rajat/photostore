## 1. [P1] Separate tabs can still overwrite a newer shared persistent snapshot

Location: `frontend/src/services/localSortIndex.ts:267–270`; analogous guards in `localPeopleIndex.ts` and `localAlbumsIndex.ts` use their own module-local generation as well.

The new fence detects invalidation only within one module instance. IndexedDB is shared across tabs, but each tab owns a separate generation counter. When tab A has an old download outstanding and tab B publishes a newer download into IndexedDB, tab A's counter remains current, so it still overwrites the shared record when it finishes.

**Reproduced with the actual loader and two independent module contexts sharing the fake IndexedDB:**

1. A receives manifest validator v2 and starts downloading a stale v1 body while rebuilding; its body completion is delayed.
2. B receives the same validator, downloads the now-published v2 body, and persists rating 5.
3. A completes with rating 1. Its own request generation still matches, so it persists the older snapshot over B's.
4. B's existing memory cache still returns 5. After a fresh module reload, the current v2 validator matches the overwritten storage record and the returned rating is **1**, expected **5**.

The dirty-v2 → clean-v2 validator sequence is realistic and is the same premise as the original single-tab reproduction. This is a remaining form of the previously identified persistence defect, not a claim that the new guard caused it. The test simulates tab isolation with independent module contexts; a live two-browser-tab race was not executed in this pass.

Use an atomic shared-storage ordering check based on the actual payload revision, rather than relying only on a tab-local counter. Compare and write within the same IndexedDB read/write transaction so another tab cannot update between the check and write. Retain the local generation check for own-tab invalidations.

## 2. [P2] Album rollback can restore a stale shadow name after reconciliation adopts another client's rename

Location: `frontend/src/mockups/prototype/store.tsx:1798–1803`; album list consumption at `frontend/src/mockups/prototype/pages/AlbumsPage.tsx:240`.

The new albumNameEditsRef retains the previous successful name independently of the central receipt. Authoritative source reconciliation updates the receipt and a fetched list, but not this shadow entry. A subsequent failed local rename therefore restores the old shadow name into the raw albums array.

**Reproduced through StoreProvider:**

1. Rename Original → First successfully, creating the shadow entry and confirmed receipt.
2. Another client renames to Remote. Accept an authoritative source response for Remote and refetch the album list; both the raw list and accessor now show Remote.
3. Try renaming to Attempt, then fail that save.
4. The central journal correctly rolls back to Remote, so albumById returns **Remote**. The shadow chain restores **First** into `store.albums` instead.

The Albums sidebar renders the raw `albums` array while the detail uses albumById, leaving contradictory names on the same page. Before the new shadow chain, this single failed rename captured Remote from the refreshed list and restored that current name; the new chain introduces this regression.

Resolve rollback state through the current journal receipt/confirmed baseline, or synchronize/prune the shadow entry when canonical values change. A previously successful shadow value must not outrank a later authoritative source value.
