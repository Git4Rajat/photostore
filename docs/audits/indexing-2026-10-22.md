# Indexing audit — 22 October 2026

Audited commit `dc96b4ba678214bdbe183de3ef66eb7218ff1709` and its indexing dependencies, plus the live `forenklaprep1-dev-rg` deployment. Azure evidence collected at approximately 2026-10-21 22:08 UTC (22 October in Stockholm). This was a read-only production inspection; no application traffic, queue consumption, infrastructure changes, or repairs were initiated.

Verdict: the image rollout succeeded, but the dedicated indexing architecture is not deployed. Two correctness gaps also need attention.

## 1. High — dedicated index maintenance is inactive in the deployed environment

The indexer is running image `dc96b4b…`, revision `forenklaprep1-dev-indexer--0000005`, with a single `APP_ROLE=indexer` container (2 CPU / 4 GiB). Its only scale rule is HTTP; max replicas remains 2. There is no `index-maintenance` sidecar, queue scaler, or configured termination grace period. `INDEX_MAINTENANCE_QUEUE_NAME` and `INDEX_BUILD_ROLES` are absent from indexer, core, and cluster configuration. Storage has no `photostore-index-maintenance` queue.

Consequently the code takes the legacy branch: index builds still run in the cluster worker, and `storage_utils.DURABLE_INDEX_UPDATES` is false. The metadata source outbox, revision-aware scheduling, and maintenance recovery loop are not active. This is a partial feature rollout, not a current total indexing outage.

Evidence: Azure Container Apps configuration, revision inventory, storage queue inventory, and post-rollout cluster logs. The intended configuration is in `deploy/resources.bicep:382`, `:987`, and `:1014`.

Action: after correcting the dedicated-mode dependency issue below, roll out the infrastructure and producer configuration together. Verify the sidecar, queue ownership, scaler, and successful processing before claiming the migration is complete. Updating the image alone does not enable it.

## 2. High — overlapping label edits can remain unprocessed on the deployed legacy path

Location: `backend/app.py:10624` and `backend/app.py:11069`–`11101`.

Reproduction: a People job captures the label/dirty snapshots and projects name Bob. A concurrent rename to Carol writes a new source token and dirty row, but `enqueue_index_build` returns `already_active` because the current People job is running. The old job's conditional acknowledgements correctly preserve Carol's records, then report completion without scheduling another job. Legacy mode has no maintenance-ledger recovery loop. Carol can remain absent from the People projection until another read or mutation schedules maintenance.

The reproduction verifies that Carol remains in the source and label-pending partition, the published projection is Bob, and no follow-up message was sent. It models a fresh running job, matching the deployed configuration. Dedicated mode's revision tracking addresses this race, but is inactive here.

Action: enable the durable path as part of a coordinated rollout, or add an explicit follow-up scheduling check to legacy completion. Preserving dirty records alone does not guarantee processing.

## 3. Medium — dedicated metadata scheduling can publish stale album covers

Location: `backend/storage_utils.py:938`–`945`; album cover consumer at `:6335`; worker scope handling at `backend/app.py:11092`.

For a rating change, `publish_metadata_index_intent` schedules `albums`, then `search`, then `sort` by alphabetically sorting index kinds. Album covers read ratings from the Search database. The Albums job can therefore publish the previous best-rated photo and mark its manifest clean before Search applies the new rating. Neither subsequent Search nor Sort scope schedules Albums again.

The reproduction creates an album with a.jpg rated 4 and b.jpg rated 1, then commits b.jpg's source rating as 5. The actual scheduling order is `albums → search → sort`; the first album build still selects a.jpg. Updating Search makes a new album build select b.jpg, but no such follow-up is queued.

This is a latent dedicated-mode defect; that mode is currently disabled in Azure. Queue ordering alone is not a reliable dependency protocol. Action: require Search catch-up before publishing dependent album covers, and preserve/defer the Albums intent if Search needs bootstrap or compaction. Alternatively schedule Albums after successful Search publication.
