## 1. [P1] A versioned receipt permanently disables later unversioned revalidation

Location: `frontend/src/services/pendingEdits.ts:149–154`.

The new `!floor` requirement rejects **all** unversioned observations after a field has any versioned evidence. The floor is persisted and is not scoped to a particular read path or cleared when the library changes how it serves data. Consequently the journal cannot discover later authoritative changes through server-paged photo responses or album fallback responses once an earlier versioned index acknowledged the edit.

Two reproductions fail:

- Save photo rating 5, acknowledge it in v1, reload journal state, then consume a fresh unversioned page at 2 with authoritative source also at 2. No reconciliation request is selected; the overlay remains **5**, expected eventual **2**. A concrete production transition is a library that previously downloaded the local index and subsequently exceeds the 200,000-photo client-index threshold, or falls back while its index is unavailable. Its photo pages are observed without a version.
- Acknowledge album name Saved in v1, make the local Albums index unavailable, and have the actual `GET /albums` fallback plus source return Later. A forced album refresh and explicit reconciliation still display **Saved**, expected eventual **Later**. This exercises the real StoreProvider fallback, not just the journal helper.

`hasPendingEdits` is false after the original acknowledgement, and these observations create no pending conflict. Repeated refreshes therefore cannot make progress while only the unversioned path is available. The persisted floor carries the issue across reload.

Unversioned rows must not discharge a newer versioned conflict as publication proof, but they still need to demand a bounded authoritative source check. Keep publication ordering and revalidation demand separate rather than making unversioned reads permanently ineligible once any versioned read has occurred.

## 2. [P2] Rotation rollback still falls back to the second edit's optimistic baseline

Location: `frontend/src/mockups/prototype/store.tsx:1366–1371`.

The new rotation chain skips failed predecessors, but it does not carry the original confirmed baseline the way the revised person-name chain does. Once every predecessor is failed, `restore` is undefined and the handler uses the current call's `previous` argument. For a second overlapping rotation, that argument is the first optimistic rotation, which may never have saved.

**Reproduced through StoreProvider:** start from saved 90, queue 180 with previous 90, then queue 270 with previous 180. Fail both serialized saves. Both journal fields roll back correctly, but the second store catch applies **180**, expected **90**. This is the same failing reproduction from the previous audit; the new chain has not corrected its fallback value.

Store the confirmed baseline from before the transaction chain began, propagate it through overlapping attempts, and use it after skipping failed predecessors. Prefer deriving visible rollback state from the current journal receipt plus that baseline to avoid competing transaction chains.
